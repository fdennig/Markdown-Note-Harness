# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A Sublime Text 4 package (lives in `Packages/Markdown-Note-Harness/`) that extends Markdown editing with wiki-linking, todo syncing, email reply, and Office-to-Markdown conversion. It depends on the MarkdownEditing package and overrides some of its commands.

`README.md` is the map — the file table, the command list and the diagrams. This file is the reference. They go stale in different ways, so when a module or a palette command is added or removed, both change or neither is trustworthy.

## Architecture

**Three Python plugin modules, loaded automatically by Sublime Text:**

- `francis.py` — Seven `sublime_plugin` commands, plus shared frontmatter helpers (`parse_frontmatter`, `frontmatter_field`, `read_frontmatter`, `outlook_refs`):
  - `OpenLinkedFileCommand` (TextCommand) — opens the URL or file path from a Markdown link `[text](path)` under the caret. Bound to F12 in markdown link scope. The target is read off the **scope map** (`markup.underline.link`, which the syntax puts on the target of an inline link and nothing else), not re-parsed out of the text: a bare target may contain balanced parentheses and the syntax tracks them (`link-url-unquoted-parens`), so scanning for the first `)` after the caret truncates every SharePoint link whose folder is named like `0A Initiative wide documents (workplan,concept,governance)` — as does a `)` in the *description*. Truncation is worse than an error, because a truncated `https://` URL still opens, silently, at the wrong address. The `<…>` form is the only one that may carry spaces, and its `<`/`>` are punctuation, outside the scoped target — but the quotes in the `<"C:\path\file.docx">` form the Outlook export writes are not, hence `clean`. Note `open_file`'s URL test is a *domain-shaped* regex ending in `\S+$`: a target with unencoded spaces, or any non-http scheme (`mailto:`, `file:///`, `onenote:`), fails it and falls through to being joined to the note's folder.
  - `OpenFrontmatterAttachmentCommand` (TextCommand) — opens attachment files referenced in YAML frontmatter (prepends `./attachments/`). Bound to F12 in `entity.name.attachment.yaml` scope.
  - `ConvertToMarkdownCommand` (WindowCommand) — converts .docx/.pptx/.pdf to Markdown using Pandoc or marker-pdf. Hardcoded tool paths point to `C:\portablePrograms\`.
  - `ReplyToEmailCommand` (TextCommand) — parses `from_email` and `subject` from YAML frontmatter and opens a `mailto:` link.
  - `OpenFrontmatterSymbolCommand` (WindowCommand) — finds files by an indexed frontmatter symbol and either browses them in a quick panel with frontmatter-folded previews or opens them all in tabs. Symbol-agnostic: takes `symbol`, `label`, and `pick` args. Registered for `toreply_note` in `francis.sublime-commands`.
  - `BrowseEmailsCommand` (WindowCommand) + `EmailListInput` (ListInputHandler) — browses all emails, narrowing by `/toreply`, `/priority`, `/personal`, and swapping the searchable field with `/subject` / `/sender`. Every `/` row lives in the same list as the emails, so typing `/` just fuzzy-filters to them; there is no callback for typing, so a keystroke cannot switch modes. Choosing one returns a new handler, which is what draws the chip and re-populates the list. `preview()` is the `on_highlight` equivalent and does the transient open plus fold. `EmailListInput.depth` is tracked separately from `applied` because a field flip is a step that adds no filter.
  - `OutlookMailActionCommand` (TextCommand) — opens / replies / replies-all / forwards the live Outlook item a note was exported from, by shelling out to `outlook_bridge.ps1`. One command parameterised by `action`, the same shape as `open_frontmatter_symbol`; `action: "resolve"` touches nothing and is the safe probe. `action: "open"` is bound to F12 in the body of a markdown note — `text.html.markdown` minus every link scope, because F12 there is shared with MarkdownEditing's wiki / reference / footnote jumps and with this package's own link and attachment bindings (see the keybindings note below; the subtraction, not the ordering, is what protects them). No scope tells an email note from any other markdown file, so `is_enabled` is what keeps that wide binding honest: it runs the same two tests `run` does, via the shared `outlook_lookup`, and without it every F12 in `todoUNDP.md` would spawn PowerShell for a certain failure. It sends the refs *and* `subject`/`from_email`/`date` every time and lets the bridge choose the path — a note with an `outlook:` block resolves by `entry_id` + `store_id` in one `GetItemFromID`; one without is found by subject, narrowed by sender then date. The whole chain runs inside a single bridge invocation, so the plugin orchestrates nothing: it reads `matched_by` and reports. A `search_ui` result means **nothing was opened** — Outlook is showing search results — and the status message must say so. A stale `entry_id` reports and stops rather than falling back; the block carries `store_id` too, so failure there means the message really moved. `sent:` notes reach neither path.

- `TodoSync.py` — mirrors unchecked todos from classified notes into `todoUNDP.md`. **The notes are the source of truth**; every pass re-derives the overview from them and nothing about which todos exist is stored anywhere else. Four steps: *scope* (`window.symbol_locations("<class>_note")` for each class in `TodoSync.sublime-settings`, so no note is opened just to learn whether it counts — this is what keeps the ~1700 email notes out of the sweep), *sweep* (`os.stat` each path, read only what changed, one regex per file), *diff* against the cache to find what was ticked in its own note, *render* the delimited generated zone of the overview. On save of `todoUNDP.md` the reverse runs: ticks and `!` toggles inside the generated zone are written back into the source notes, then the whole thing is swept and rendered again.
  - `todoUNDP.md` has three zones: a hand-written `# Capture` zone above the `todosync:begin` marker (swept like any other note, which is why todos typed into the overview need no special case), the generated zone between the markers, and the `## Completed` history below `todosync:end`. Only the middle one is ever rewritten. History is authoritative and is *not* re-derived, so pruning `- [x]` lines out of source notes does not disturb it.
  - `todoUNDP.cache.json` is **derived, never authoritative** — delete it and the next sweep rebuilds it identically. It gates reads on `(mtime, size)`, lets a sweep tell *completed* (moved unchecked→checked) from *deleted* (vanished), and locates the source line behind an overview line so the wiki link does not have to carry a path.
  - Urgency is a **boolean on the entry, not part of the text**, so toggling `!` cannot change a todo's identity.
  - **Two gates make per-save sweeping cheap.** `watched()` answers "can saving this file change the overview?" from the buffer already in hand — its frontmatter class, no index call and no file read — so saving one of the ~1700 email notes costs a single regex and nothing else. And `render()` compares the rendered bytes against what is on disk and skips the write when they match; since renders are idempotent, `todoUNDP.md` is only ever touched when a todo actually moved. Without that comparison every save produced a OneDrive sync event and reverted the open view. The `_Updated` stamp is excluded from the comparison, so it reads as *when the todos last changed*, not *when the last sweep ran*.
  - **A cold index cannot blank the overview**, because the index is not the only witness to scope: a note already cached with a qualifying class stays in scope whatever the index currently says, and `extra` lets a save carry in a note classified moments ago. So a note classified for the first time appears on that very save, with no indexing wait. `guard_empty_scope` is only the last resort, for when neither the index nor the cache can vouch for a single note. It is deliberately **not** proportional — an earlier `min_scope_ratio` would have read a deliberate narrowing of `classes` as a fault and refused to apply it.
  - Replaced an accumulator that read `view.indexed_symbol_regions()` one saved file at a time into `todo.yml`. That design could not see the vault (70 tracked against ~285 on disk), could not forget a deleted line, and used the *transformed symbol name* as its primary key — so a change to `symbolIndexTransformation` silently duplicated every todo containing a link. `todo.yml` is retired; its `resolved_todos` were merged into the history block.

- `WikiResolve.py` — the **editor-shaped half** of wiki resolution: it stamps the derived `from_wiki:` / `to_wiki:` (and `organizer_wiki:` / `attendees_wiki:`) keys onto the note you are **saving**, and does nothing else. All the logic lives in the *vault* at `<vault>/scripts/wikiresolve_core.py`, shared with `<vault>/scripts/resolve_wiki.py`, which owns the corpus pass. Resolution exists because the two naming schemes never met: the macro writes display names (`from: "[[@Demba Tandia]]"`), person notes are camelCase basenames, and 12,600 of 13,733 wikilink occurrences in the vault (92%) pointed at no file. Consumed by the graphify integration (`.claude/plans/floating-watching-mochi.md`) and §4/§6 of the *vault's* `CLAUDE.md`.
  - **Half of this feature is not in this repository.** `WikiResolve.py`, `WikiResolve.sublime-settings` and `tests/test_wikiresolve.py` are here; `scripts/wikiresolve_core.py`, `scripts/resolve_wiki.py` and `scripts/tests/test_wikiresolve_core.py` are in the vault and versioned with it. A commit here is never the whole change, and a bisect that only walks this repo cannot explain a behaviour change in the tiers.
  - **Why the split, and do not undo it.** The batch pass used to live here and caused two incidents, both in Sublime's lifecycle rather than in the logic: a startup sweep that rewrote 1,745 notes three seconds after the plugin was first written, because its setting defaulted the wrong way; and a crash on **every email note opened**, because `on_load_async` wrote the file and then called `revert` on that view from inside the view's own load callback. Neither was reachable by the 91 headless tests — the tested surface (pure text transformation) and the risky surface (plugin lifecycle) barely overlapped. A command you invoke, whose report you read before it writes, is the right shape for batch work.
  - **What the plugin still does:** `on_pre_save` edits the buffer being written (no second write, nothing to revert), and `on_load_async` writes the file you just opened, so notes arriving from the macro are resolved when you first read them. **`on_load_async` must never revert the view** — that was the crash, and Sublime's own watcher reloads a clean buffer anyway. Both are per-note, both announce a change in the status bar rather than writing silently, and the `on_load` setting turns the second off in one edit.
  - **What is gone from the plugin:** the corpus sweep, the dry-run report, the cleanup pass, the `(mtime, size, gaps, fingerprint)` cache, and the `self_people` setting. Two simplifications fell out of the move — there is **no cache at all** (a deliberate run reads every note in ~2 s warm), and discovery is a plain `os.walk` rather than `window.symbol_locations`, so the plugin and the script see exactly the same notes and both are reproducible outside the editor.
  - **The core has two constraints that are easy to break.** No `import sublime`, so the CLI needs no stubs; and Python **3.3** compatible, because the plugin host is — `str.format()` only, no f-strings, no `pathlib`, no `glob(recursive=True)`. The CLI and its tests run under 3.14 and may use anything.
  - The plugin locates the core by looking for `scripts/wikiresolve_core.py` under each folder open in the window, or via its `core_path` setting, and inserts that directory into `sys.path`. **If it is not found every hook is a no-op** and says so once in `Data/Logs/WikiResolve.log`. The logic sits in the vault rather than in this package so the batch script does not depend on Sublime's install path — the coupling the split exists to remove.
  - **Four match tiers, and deliberately not five.** t0 an address (`from_email:`, or a recipient written as a bare address in brackets — 597 of 10,057 recipient entries are), t1 an exact normalised `aliases:` entry, t2 the note's title or its basename (camel-split **and** verbatim — `[[silviaKuehl]]` normalises to `silviakuehl`, which the split form does not match), t3 token-set equality so `Inguscio Agostino` meets `Agostino Inguscio`. **t4 (bare first names by token subset) is not implemented** because it collides. Measured on the real corpus: t1 does 6,036 of 11,803 entries and t2+t3 together do 15 — the curated `aliases:` lists are the mechanism. `norm()` is a behaviour-for-behaviour port of `Norm()` in the vault's `build_alias_harvest.ps1`, and it runs on **both** the stored key and the query, which is why `cristina.altomare@undp.org` stored as `'cristina altomare@undp org'` is harmless.
  - **A key reachable from two person notes resolves to nothing**, is stored as `None` (present, so the lookup stops there) and is reported. Never guessed. A new collision now raises a status message on index rebuild, because it used to be visible only if you went looking — the vault's one live collision (`simoneMarino` vs `simoneMarinoGoverno`) silently costs 84 entries.
  - **Nothing records the misses in the note.** No `to_unresolved:`, no report file: the gap between the `to:` item count and the `to_wiki:` item count *is* the audit. Unresolved and ambiguous names reach the script's report and the log, nowhere else.
  - **Always write the key.** Empty means *resolved to nothing*; **absent** means the resolver has never run. An empty scalar is written `from_wiki:` with **no trailing space** — with `trim_trailing_white_space_on_save` on, that space would be stripped back out on every save and the next pass would see a difference, i.e. a rewrite loop across 1,700 files.
  - **The vault owner is marked in the note, not in settings:** `self: true` in `francis.md`. Entries resolving to a self note are dropped and counted under a `self` tier, never as gaps — counting them would make every note you appear in eligible for re-reading forever, hunting for something deliberately absent. It lives in frontmatter so the fact travels with the vault; as an editor setting, the script and any other consumer would have re-added the link to 1,661 notes. This is 1,661 of 11,803 entries.
  - **`optional_attendees:` folds into `attendees_wiki:`**; there is no `optional_attendees_wiki:`. One derived sequence per note, and the raw keys still carry the invited/attended distinction.
  - **`frontmatter_bounds` matches the opening `---` with the BOM stripped for the comparison only.** Leaving the BOM in the text means row indices are identical for a file read off disk and for that note's Sublime buffer (which has none) — one scanner, both callers, and the BOM cannot be dropped in transit. Reads and writes both use `encoding="utf-8", newline=""`; `utf-8-sig` on the *write* would add a BOM to files that never had one.
  - **Classification uses `head_class`, not `block_class`.** `block_class` requires the closing `---`, which a note with a hundred recipients plus an Outlook `store_id` can push past any sane read window — the note would then be silently skipped. `head_class` needs only the opening delimiter, so the classify read is 2 KB.
  - **Generative is monotone; only the script's `--reconcile` removes anything.** Every automatic path fills an empty key and appends newly resolved names, and **never clears a value or shortens a list** — so an incomplete index (a half-migrated vault, a root that failed to mount) cannot silently delete every link to someone. `RECONCILE` is exact: it drops self links, clears what the index cannot explain, and relocates a key to its current anchor. Both idempotent.
  - Relocation exists because the 1,745 notes backfilled on 20260809 carry `from_wiki` **above** `from_email:`; the anchor was corrected afterwards and `_splice` replaces in place by design. A move is an insert plus a delete, safe only because edits apply in descending row order — an anchor *inside* the old span would break that, so that case falls back to replacing in place.
  - The in-memory index is the only state the plugin holds, and it exists solely because `on_pre_save` runs on the main thread and must answer in microseconds (measured: 528 KB deep, ~150 ms to build warm, living in `plugin_host-3.3.exe` rather than Sublime's own process). Built 3 s after `plugin_loaded`; a saved person note triggers an **incremental** refresh — re-read that one note, rebuild the four tables from records already in hand — rather than the full walk the old design did on every person save. If the on-save stamp is ever dropped, the whole module goes with it.
  - **The index only ever learns from a save inside Sublime.** `on_post_save_async` is the sole automatic refresh, and it fires on a *person* note. A person note added or edited outside the editor — by a script, by OneDrive sync, by the other machine — is invisible until *Wiki: Rebuild person index*, and the symptom is a name that resolves everywhere except in Sublime. The two palette entries are diagnostics and nothing else: `wiki_resolve_show_index` lists every person note the resolver can see with its address and alias counts, the `self` marker, and any ambiguous key at the top; `wiki_resolve_rebuild_index` re-walks the roots. Neither writes a note. The corpus pass is not a command at all — it is `scripts/resolve_wiki.py` in the vault, deliberately, per the split above.
  - **The settings surface is six keys**, all in `WikiResolve.sublime-settings`: `core_path` (empty = look for `scripts/wikiresolve_core.py` under each folder open in the window), `person_classes`, `person_roots` (empty = the window's folders, which is what makes the vault owner's note findable when it sits outside the vault tree — but it also means the plugin and `resolve_wiki.py` agree only when they walk the same roots, so pin it if that matters), `exclude` (`*_template.md` must stay: the template's `email:` and `aliases:` are empty placeholders), `on_load`, and `verbose`. Three keys are **gone** and the file records where each went: `self_people` → `self: true` in the person note, `startup_sweep` → removed with the sweep, `leaf_classes` → `LEAF_SPEC` in `wikiresolve_core.py`, which also names which keys each class carries.

- `WikiLinks.py` — **backlinks, rename and the note picker, answered from the symbol index instead of by reading the vault.** MarkdownEditing's `mde_list_back_links` walks every project folder and reads every `.md` looking for `[[<basename>]]`: ~2,400 files per invocation, over OneDrive, uncached. The whole feature rests on one observation — **a wiki link target *is* a filename** (the vault's rule is a globally unique basename with no path), so the name to query is never something that must be discovered; it is sitting in the directory listing. Scope the targets, index them as **references**, and "who links to X?" is one native lookup.
  - **References, not definitions.** `showInIndexedReferenceList`, queried with `window.symbol_locations(name, SYMBOL_SOURCE_ANY, SYMBOL_TYPE_REFERENCE)`. A link is a *use* of a note, not a declaration of one — and the definition namespace is flat and already shared with the `_note` tokens and MarkdownEditing's `#`-prefixed headings. `SYMBOL_SOURCE_ANY` rather than `SYMBOL_SOURCE_INDEX` so an open, freshly-edited buffer counts too.
  - **The index cannot be enumerated, and this design never needs it to be.** Every window-level API takes a symbol *string* (`symbol_locations`, `lookup_references_in_index`); only `View.indexed_references()` lists anything, and that needs the file open in a view. The on-disk index is LevelDB (`Data/Index/*.ldb`). So "what are all the links?" is not answerable from Sublime at sane cost, while "who links to X?" is instant — which is exactly why the whole-vault adjacency graph is **not** here and belongs to a vault-side pass, the same split `wikiresolve_core.py` already makes.
  - **Wiki links inside markdown headings and inside open todos are not indexed, and every rename says so.** Indexing them shredded the heading's or the todo's own symbol; the mechanism, the measurement and the experiment are under `Reference List - Wiki Body.tmPreferences` below. The consequence here is that `wiki_backlinks` does not list them and `wiki_rename_note` does not rewrite them, so `SKIPPED_NOTE` goes into the confirmation dialog and into `Data/Logs/WikiLinks.log` on every run. Frontmatter links are unaffected — nothing else claims a scope inside `meta.email.wikilink-line.yaml`, and the YAML package's own symbol list covers anchors only.
  - **Only rows the index reported are rewritten.** A raw `to:` line can hold a bare `[[francis]]` too — 2,286 of them do — and those keys are the macro's audit trail, never edited from this side. Rewriting by line scan rather than by reported row would break that contract silently.
  - **The row base is measured, not assumed** (`detect_row_base`). `SymbolLocation.row` feeds `path_encoded_position()`, which is 1-based, but the API reference does not promise it, and a silent off-by-one would rewrite the line *above* every link in the vault. Under the correct base every reported row lands on a line that actually holds the link; if neither base fits, the file has moved on since it was indexed and the location is reported and skipped, never guessed at.
  - Replacement is `[[old]]` → `[[new]]` **with the brackets**, so renaming `francis` cannot corrupt `[[francisDennig]]`. It is also line-based, which is why there is no descending-order dance: replacing inside a line never moves another line, so the offset shifting character-level edits must sort around does not arise.
  - A rename **refuses to run while any affected file is dirty**, because the rewrite goes to disk underneath open buffers. It renames the file last and `retarget`s the open view. Every run is logged to `Data/Logs/WikiLinks.log`.
  - **The subject of a backlink query is the note in view, and the caret does not change it.** `target_name` used to prefer `name_under_caret` — so `shift+f12` reported the note in view, *except* when the cursor happened to be resting in a `[[link]]`, where it silently reported that other note instead. The panel lists paths and never names what it is about, so the two cases are indistinguishable once it is open: the answer to "who links here?" depended on where the cursor was left. The caret reading is still worth having and is kept as `wiki_backlinks {"under_caret": true}`, palette entry *Wiki: Show backlinks to link under caret*, falling back to the note in view outside a link. `wiki_rename_note` was never caret-driven; it has always taken the open file.
  - **The count in the confirmation dialog is the completeness check.** Whether the index has seen the whole vault is the one property a lookup cannot report on itself, so recognising the number before it is written is what stands in for a cross-check. *Wiki: Show backlinks* shows the same set row by row.
  - **The picker is the same observation run backwards** — not *who links to X?* but *what is there to link to?* — and it leans on a **different index entry**: frontmatter `class: X` is already indexed as the symbol `X_note` by `Symbol List - Email Flags.tmPreferences`, so `class_notes()` is one `symbol_locations(cls + "_note", SYMBOL_SOURCE_INDEX)` per class and opens no file. `mde_make_page_reference`, which it replaces, built its list by stat-ing every file in every project folder and had no notion of what kind of note it was offering.
    - **Index-only, and the gap is the point.** A note with no `class:` key produces no symbol and is therefore not a candidate — 124 files here, all of `#countries/` including the weekly Country Updates. There is deliberately no directory-walk fallback: classifying a note is what makes it a link target, and a fallback would hide that. `basename_index()` still walks, but only to validate a rename.
    - **`hidden_classes` exists because of the shape of the corpus**, not as a preference: `email` is 1,746 of the 2,259 classified notes and its basenames run to 60 characters, so unfiltered it buries the ~510 rows actually worth linking to. `/email` is how they get in.
    - **The `/class` rows UNION, where `BrowseEmailsCommand`'s intersect.** A note carries exactly one `class:`, so intersecting `/person` with `/organisation` would always give the empty set. Everything else about `WikiNoteListInput` is `EmailListInput`'s shape — the `/` rows in the same list so typing `/` fuzzy-filters to them, a fresh handler per step to draw the chip, `step{N}` argument names. Two differences: `depth` *is* the filter count (there is no field flip), and there is **no `preview()`** — this is a `TextCommand` that must still write into `self.view`, and a transient preview would move the active view out from under it.
    - **One command, two phases, and the palette is opened by hand.** Phase 1 (no `region` arg) rewrites the bracket pair to `[[seed]]` and *then* fires `show_overlay` at itself; phase 2 (`region` present) replaces the text inside those brackets with the chosen name. That `show_overlay` call is verbatim what `sublime_plugin.TextCommand.run_` does in its `'required positional argument'` branch — but relying on *that* branch would mean `run()` never executes before the overlay, so the bracket could not be doubled first and there would be nowhere to put `region`. `region` is passed rather than re-derived so a seed holding a stray bracket cannot mis-target the write; nothing can move underneath it, because the overlay is modal.
    - `bracket_span()` serves **both** tab bindings: widening one character each way when the neighbour is another bracket is the only thing separating `[x]` from `[[x]]`. It returns `None` rather than guessing when the text between the brackets holds a bracket of its own, and phase 1 then inserts a fresh `[[]]` at the caret — which is what makes the palette entry work from open prose.
  - Reaches `francis.py` for presentation only (`parse_email_filename`, the preview folding) via a lazy `sys.modules` lookup, never an import: the package directory contains hyphens, so it is not importable by name, and a relative import at module level would run before Sublime has necessarily loaded the sibling. `None` is survivable everywhere it is used.

**Syntax extensions:**

- `MarkdownExtended.sublime-syntax` — extends the built-in Markdown syntax to scope the text of unchecked todo items as `entity.name.tag.todo.open.markdown` / `.urgent.markdown`. Colour and the per-file `ctrl+R` list only; TodoSync reads todos from the notes, not from these scopes. The urgent context is entered on a **lookahead**, so the `!` sits inside the scope rather than being consumed on the way in.
- `YAMLEmailFrontmatter.sublime-syntax` — extends YAML syntax with scopes for email fields (sender, from_email, subject, attachments, toreply), and for the **wiki link targets** in the five frontmatter keys that hold basenames: `from_wiki:`, `organizer_wiki:` and `responsible:` as scalars, `to_wiki:` and `attendees_wiki:` as sequences, scoped `entity.name.wikilink.<relation>.yaml`.
  - **What decides whether a key is scoped is what its value points *at*, not who writes it.** The raw `from:` / `to:` / `organizer:` / `attendees:` keys hold display names (`[[@Demba Tandia]]`) that resolve to no file and are never edited from this side; indexing their 9,255 occurrences would bury every real hit. `responsible:` is hand-written rather than macro-written but holds a basename, so it is in — and leaving it out would have meant renaming a person silently orphaned every activity they are accountable for.
  - **One symbol per list item, never one per key.** The sequence keys push a context that scopes each `[[name]]` on its own and pop at the next column-0 key, exactly as the `attachments:` rule does; the key line itself scopes nothing. Scoping a key's whole value would collapse a hundred recipients into one symbol whose name is not a basename, and a rename would then have one location to rewrite where it needs a hundred. Because scanning resumes mid-line after the key match, the pushed form also covers a flow sequence, while `to_wiki: []` yields no item at all.
  - **The scalar keys are matched precisely rather than by "scope any `[[..]]` after the key", and the templates are why**: `activity_template.md` and `programme_template.md` carry `responsible:   # "[[person]]" ...`, so a forgiving rule would index a phantom edge to a note called `person` out of every template in the vault. Those two comments are the *only* wikilink-bearing frontmatter comments in the corpus, and the precise rule is what excludes them.
  - The captured group is the **bare name** — quotes and brackets are consumed outside it — so the indexed symbol is literally the text in the file and no `symbolIndexTransformation` is involved anywhere in this feature.

**Symbol list / indexing:**

- `Symbol List - ToDos.tmPreferences` — puts unchecked todos in the **per-file** symbol list (`ctrl+R`) only. `showInIndexedSymbolList` is deliberately `0`: nothing reads todos from the project index any more, and while it was `1` the index stored *transformed* names, which made a todo's identity hostage to a regex in this file. **This file is also one of the two casualties of the wiki reference scopes** — see `- entity.name.tag.todo` under `Reference List - Wiki Body.tmPreferences` below. 304 of the 497 open todos contain a wiki link, and while the wiki entry won inside them every one of those `ctrl+R` rows was cut into fragments around the link.
- `Symbol List - Email Flags.tmPreferences` — indexes frontmatter flags. The syntax scopes whole `key: value` pairs as `entity.name.email.flag.yaml`; this file's `symbolIndexTransformation` rewrites each pair into its own token. The boolean flags are enumerated (`toreply_note`, `personal_note`, `sent_note`, `priority_note`) because their values are pinned in the syntax. **`class` is not enumerated**: one capturing substitution turns any `class: X` into `X_note`, so a class invented in a note is findable via `window.symbol_locations("X_note")` with no change to this package — which is what lets `TodoSync.sublime-settings` name the classes it sweeps. `class: email` still yields `email_note`, which the email commands depend on.
- `Reference List - Wiki Body.tmPreferences` / `Reference List - Wiki Frontmatter.tmPreferences` — index wiki link targets as **references** (`showInIndexedReferenceList`), never definitions and never in the per-file list. This is what `WikiLinks.py` queries. Two files rather than one because a `.tmPreferences` is keyed by scope, so this is where a per-relation `kind` can differ.
  - The body selector subtracts four times: `meta.link.reference.wiki.description.markdown - punctuation.definition.link.begin.markdown - punctuation.definition.link.end.markdown - markup.heading - entity.name.tag.todo`, and **no subtraction is tidiness**. **Both brackets fall inside the meta scope** — `meta_scope` covers the text of the pushing match and of the popping one alike, which is the whole difference between it and `meta_content_scope` — so both punctuation scopes have to come off to leave the bare name.
  - **The begin subtraction was missing until 20260813, and every body wiki link in the vault was indexed as `[[name`.** The lookup `symbol_locations("francis", …, SYMBOL_TYPE_REFERENCE)` therefore returned frontmatter hits only, so *Wiki: Show backlinks* answered from `to_wiki:`/`from_wiki:` and silently omitted the ~2,100 plain-body links, and *Wiki: Rename note and backlinks* left every one of them stale. It hid because `name_under_caret` in `WikiLinks.py` held the same false premise — from the same paragraph of notes — and stripped a trailing `]]` without a leading `[[`, so `shift+f12` **on** a body link queried `"[[francis"`, matched the equally wrong index name and looked correct, while `shift+f12` anywhere else in the note queried `"francis"` and did not. The two wrongs were symmetrical, which is why the feature appeared to work in exactly the way it was usually exercised, and why fixing either one alone breaks it outright. They change together.
  - **The reference counts recorded here are modelled, and a model cannot disagree with the thing it models** — which is how the above survived being written down as measured. The authority on what the index holds is the index, and it is legible: `grep -a -o '\[\[[A-Za-z0-9][A-Za-z0-9 ._-]\{2,30\}' Data/Index/*.ldb | sort | uniq -c` is what showed `[[eligible4ODA`, `[[MASE`, `[[CDP` stored verbatim, alongside frontmatter names stored bare. Settle any future claim that a scope reaches the index there, not in a Python model of the selector. Note also that **a `.tmPreferences` change does not re-index anything**: close Sublime, delete `Data/Index/`, reopen.
  - **`- markup.heading` and `- entity.name.tag.todo` are the price of keeping those two things in their symbol lists, and both were paid after the bug, not before it.** A `.tmPreferences` entry does not add to what other entries say: at each point the **highest scoring selector wins** and its settings are the only ones that apply. This entry matches two scopes, one of them deep on the stack, so it outscores anything matching the container — MarkdownEditing's `Symbol List - Heading` (`markup.heading`, index 1) and this package's own `Symbol List - ToDos` (`entity.name.tag.todo.open.markdown`, index 2) both lose to a match on `meta.link.reference.wiki…` at index 3. Since this entry says `showInSymbolList 0` / `showInIndexedSymbolList 0`, winning inside one of them punched a hole mid-line and the container's symbol region shattered around it. The visible symptom was a project symbol literally called `]]`; the real loss was the heading and todo text, which stopped being findable under the words it is written with, in both `ctrl+R` and `ctrl+shift+R`. MarkdownEditing uses the same mechanism on purpose in `Symbol List - Hide.tmPreferences`, which punches `meta.toc-list.id` out of a heading — harmless only because an id sits at the *end* of the line, so one run survives. A wiki link sits in the middle, so two fragments do.
  - **What the subtractions cost, measured rather than guessed, and the two containers are not alike.** *Headings*: 219 of them hold 477 links, nearly all `## people: [[a]] [[b]]` in the meeting logs, but only **233 occurrences point at a note that exists** and of the 211 names reachable *only* from a heading exactly **2** are real notes (`giorgiaCaropreso`, `simonaRuggieri`) — the rest are dangling short forms like `[[mpho]]` and `[[john??]]` that no rename could ever have touched. *Todos*: 304 of the 497 open ones hold 468 links and these are the expensive ones — **464 of 468 point at a real note**, and six notes are reachable only from a todo. Together ~700 real backlink rows go unlisted and a rename leaves those links stale, in the most actively edited part of the vault. So it is a blind spot worth stating, and `WikiLinks.py` states it in the rename dialog and in the log on **every** run (`SKIPPED_NOTE`) rather than letting a rename quietly skip a link.
  - **The experiment that would buy them all back is a third entry, not a looser selector, and it ships inert as `Reference List - Wiki In Symbols.tmPreferences.disabled`.** It scopes the target only *inside* a heading or a todo, which outscores both this entry and the container's, and sets all three list keys to 1 — so the points stay flagged for the list their container wanted them in and are offered as references as well. Whether that keeps the container whole turns on something **undocumented and unfindable**: whether Sublime builds a symbol region from adjacent points that are merely all *flagged*, or only from adjacent points owned by the same *entry*. Neither the API reference nor the symbols documentation says (the latter 404s), and no headless test reproduces the indexer, so the only way to know is to enable it and press `ctrl+R`. If *flagged* wins, the containers stay intact, all ~945 links come back and the two subtractions can go; if *entry* wins, nothing is worse than it was when the bug was reported. Known cost even in the good case: bare names reach the **definition** namespace, which is flat and shared with the `_note` tokens — splitting the entry in two (headings keep `showInIndexedSymbolList 1`, todos go back to `0`) confines that to headings. It is `.disabled` rather than absent because a `.tmPreferences` is found **recursively**, so a subdirectory would not have disabled it; the extension is the switch.
  - The frontmatter selector is the prefix `entity.name.wikilink`, so a relation added to the syntax later is indexed with no change here.
  - **Neither carries a `symbolIndexTransformation`**, which is the point: the selectors already yield exactly the target name, so the indexed symbol is literally the text in the file and a rename can compare it against a filename with no decoding step between. Contrast `Symbol List - ToDos.tmPreferences` above, which records what it cost once to make an identity hostage to a regex.
  - `kind` is set on both, differently, but **nothing depends on it**. No shipped package on this machine uses the key, so whether it survives into `SymbolLocation.kind` on an indexed *reference* is unverified; `WikiLinks.py` labels a row by kind when one is there and behaves identically when it is not. The two values differ only so the question can be settled by looking at a result.

**Outlook macros (`outlook_macros/`):**

VBA that runs inside Outlook, not inside Sublime. It is the *producer* of every email note the plugin consumes, so the two halves live together — but nothing here is loaded or executed by Sublime. Editing a `.vba` file changes nothing until it is pasted into Outlook's VBE (Alt+F11) and the module is re-imported.

- `vba/SaveEmail.vba` — `ExtractEmail`, `ExtractEmailToReply`, `ExtractEmailWithAttachments`, `ExtractEmailPersonal`, `ExtractEmailHighPriority` all funnel into `ExtractEmailCore(toReply, saveAttachments, isPersonal, priority)`; `ExtractMeetingCore` handles appointments and `SendAndSaveEmail` sends outgoing mail and archives it with `sent: true`.
- `vba/SaveUtilities.vba` — filename sanitising (`ReplaceCharsForFileName`), `formatName` (wraps people as `[[@Name]]`), and `SaveAsUTF8`, which writes a **BOM** — hence `read_frontmatter` opening files as `utf-8-sig`.
- `vba/USER_CONFIG.vba` — vault paths and filename prefixes. Contains machine-specific absolute paths.

Imported with `git subtree` from `https://github.com/fdennig/outlook2markdown.git` (itself a fork of machado-t/Outlook2Obsidian, MIT — `outlook_macros/LICENSE` must stay with the code). To sync either way:

```
git subtree pull --prefix=outlook_macros https://github.com/fdennig/outlook2markdown.git main
git subtree push --prefix=outlook_macros https://github.com/fdennig/outlook2markdown.git main
```

**The macro/plugin contract** — change one side and the other breaks silently:

- Frontmatter values are pinned in `YAMLEmailFrontmatter.sublime-syntax`, so the macro's exact spellings matter: `toreply: true`, `personal: true`, `sent: true`, `priority: high`, `class: email`, `class: meeting`. `ExtractEmailCore` writes `toreply: `, `personal: ` and `priority: ` *empty* when the flag is off — those lines deliberately fail to match and never reach the symbol index.
- Filenames are `<prefix><yyyy-MM-dd>_<HHNN> @<sender> - <subject>.md`, meetings omitting ` @<sender>`. `EMAIL_FILENAME_RE` in `francis.py` parses this and is the reason email discovery opens no files. Changing the prefix is safe (the regex anchors on the date token); changing the separators is not.
- `read_entry_fields` reads `from`/`sender`, `subject` and `date` from frontmatter as the fallback for names that don't match.
- **Outlook back-references.** `ExtractEmailCore` closes the frontmatter with an `outlook:` sequence holding `entry_id`, `store_id`, `message_id` (omitted when unavailable) and `conversation_id`; `ExtractMeetingCore` writes the first two; `SendAndSaveEmail` can only write `conversation_id`, because `.Send` re-keys the item's EntryID and the Message-ID is stamped by the transport. They exist so that something can act on the live Outlook item inside its original thread, which no `mailto:` can do. `outlook_refs()` in `francis.py` reads them and `OutlookMailActionCommand` acts on them via `outlook_bridge.ps1`; only `entry_id` + `store_id` are used so far, so `message_id` and `conversation_id` are carried but not yet consumed. `outlookReplyProposal.md` holds the design for the search tiers that would consume them and, more usefully, what testing against a real profile disproved. Two consequences of the sequence shape: it folds to one line like `attachments:` does, which is why it is a sequence and why it goes last; and `frontmatter_field` **cannot read it** (that regex anchors keys at column 0), hence `outlook_refs`. They are deliberately **not** scoped or indexed: they are opaque per-item values and every indexed symbol shares one flat namespace.
- The note's `subject` is the **raw** Outlook subject (via `YamlQuoted` in `SaveUtilities.vba`); only the filename copy goes through `ReplaceCharsForFileName`. Before that split, filename sanitising silently stripped `: ? / \ " < > | [ ]` out of the frontmatter too. Notes exported before the change still carry the stripped form, so nothing may rely on `subject` matching Outlook exactly.
- **`from:` / `to:` hold display names, and `*_wiki:` is the plugin's answer to that.** The macro writes `from: "[[@Demba Tandia]]"` and `to:` as a block sequence of `"[[@Name]]"` — never a person-note basename, and 353 of the 1,721 notes use the bare form without the `@`. The resolver — `<vault>/scripts/wikiresolve_core.py`, driven either by `resolve_wiki.py` or by the plugin's on-save hook — owns the derived `from_wiki:` / `to_wiki:` keys and **only** those; the raw keys are the macro's and are never edited from this side. So emitting `from_wiki:`/`to_wiki:` *from the macro* would make the two co-owners of one key — at which point the contract of "absent means the resolver has never run" stops being true and the pass loses the signal that tells it what to fix. If the macro is ever taught to resolve, it should write the keys **empty**, not resolved.
- **`to_email:` is the macro's side of resolution, and its contract is positional.** `ExtractEmailCore` and `SendAndSaveEmail` write one address per `to:` entry, in the same order, via `GetRecipSmtp` — which is why that function **never returns an empty string**. `LEAF_SPEC` pairs the two lists only when their lengths agree, and `seq_values` discards empty items, so a single blank line does not cost one address: it throws away every address on the note and drops it back to matching display names. A placeholder that matches nothing is therefore strictly better than a gap, and costs nothing, because a non-matching address still falls through to the name tiers. This is what turns the 6,036 t1 name matches into exact t0 address lookups and demotes `aliases:` from load-bearing infrastructure to a convenience — for **new** notes only; the 1,722 already exported have no `to_email:` and still resolve by name.
- **An empty sequence is written `key: []`, by `YamlSeq`.** Not a bare `key:` with nothing under it, which YAML reads as null rather than as an empty list, and not a missing key — the resolver distinguishes *no recipients* from *the macro never wrote this*. `attachments:` and `optional_attendees:` already used the convention; `YamlSeq` is what makes `to:` and `to_email:` follow it, and it is also the reason those two keys stay length-matched when a mail has no recipients at all.
- **`to:` is every recipient — To, Cc and Bcc alike — and there is no `cc:` key.** It has always been the whole `Recipients` collection and `to_wiki:` is derived from it, so narrowing it to To would silently change what the graph says about the existing corpus. A `cc:` split was built and then removed on purpose: Cc is not used consistently enough to carry meaning — whether someone was addressed or copied says more about the sender's habits than about who the message concerned — so the key would have invited inferences the data does not support. `bcc:` is absent for the same reason plus one more: it exists only on outgoing notes, and naming it would put the fact that a message was blind-copied into a note read over shoulders. Note the `Recipients` collection is **not** ordered To-then-Cc (measured on a live item whose Cc entries came first), so position in `to:` ranks nothing — it only has to match `to_email:`.
- **The sender's address comes from `PR_SENDER_SMTP_ADDRESS` (`0x5D01001F`); a recipient's comes from `PR_SMTP_ADDRESS` (`0x39FE001E`).** They are not interchangeable and each is useless in the other's place — `GetSenderSmtp`'s fallback read the recipient tag for a while and so silently produced nothing whenever `GetExchangeUser` failed. Same trap `outlook_bridge.ps1` documents.
- **`AddressEntry.Type = "EX"` does not mean the entry is a person, so never chain off `GetExchangeUser`.** It returns `Nothing` for a distribution list, a room or equipment mailbox, a public folder, and any entry the address book could not resolve; `.PrimarySmtpAddress` on `Nothing` is run-time error 91, which is what one group in a To line used to cost. Assign it, test `Is Nothing`, then try `GetExchangeDistributionList` — a group's own address is a better answer for that position than the X500 DN the fallbacks reach. The surrounding `On Error Resume Next` is not a defence: with *Break on All Errors* set in the VBE (Tools → Options → General) the debugger stops inside a Resume Next region too. The same trap sat in `GetCurrentUserSmtp`, where it was quieter still: the error landed in that function's own handler, so a `Nothing` there cost the **sent** note its `from_email` and nothing said so.
- **The extract macros jump over their error handler, and the handler now reports.** `ExtractEmailCore` and `ExtractMeetingCore` release their objects and `Exit Sub` before the `EndClean:` / `EndCleanMeeting:` label, so reaching the label can only mean failure. That jump is the mechanism, not tidiness: `Err.Number` **cannot** be tested at the label, because the `On Error Resume Next` regions above leave `Err` set after a perfectly successful run and neither `Resume Next` nor a later `On Error GoTo` clears it — a handler that tested `Err` would report on every note. Until this, both labels were silent, which made a failed export indistinguishable from the macro not being wired up at all: no note, no message, nothing to search for. `SendAndSaveEmail` has always reported; these now match it. There is no half-written note to clean up either way, because the file is saved only once the whole frontmatter is built.
- Wikilinks in frontmatter must be **double-quoted**, and for two different reasons: `"[[@Name]]"` unquoted is a hard YAML error (`@` is a reserved indicator that may not open a plain scalar), while `[[francis]]` unquoted is *valid* YAML for a nested flow sequence and parses silently as `[["francis"]]` — every consumer then sees a list of lists. Same rule as `aliases:` in the person notes. Everything `WikiResolve.py` writes is quoted for this reason.

## Key Design Details

- A todo's identity is `(source note, exact text)`, never text alone. The text comes from the raw line, not from a symbol name, so no transformation can change it. Ticking a box in a note needs no matching at all — the todo simply stops appearing in the sweep. Only the reverse direction (ticking in the overview) has to find a source line, and that goes through the cache: display name plus text, verified at the cached row and re-searched in that file if the note has since moved. Two notes sharing a basename are only ambiguous when the todo text repeats too; that case is reported, never guessed.
- **`WikiLinks.sublime-settings` is three keys**, all about the picker: `link_classes` (every class offered, in row order — each becomes a `/name` filter and is looked up as `<class>_note`), `hidden_classes` (listed only once asked for; `email`), and `exclude` (fnmatch globs — `*_template.md` **must stay**, since `activity_template.md` and its four siblings carry a real `class:` and would otherwise sit in the list as linkable notes). Adding a class is a settings edit and nothing else: the token is produced automatically by `Symbol List - Email Flags.tmPreferences`, and `CLASS_KINDS` falls back rather than raising for a class it has no badge for.
- **A note is swept only if its frontmatter `class:` is listed in `TodoSync.sublime-settings`** (currently `topic`, `activity`, `programme`, `person`, `organisation`), which is how the hub/leaf split reaches the todo system. Unclassified notes are silent — during the classification transition that is expected, and *Todos: Show scope* is the diagnostic: a note missing from the overview is a note missing there. Adding a class is a frontmatter edit plus a settings edit; no package change.
- To make a new frontmatter **flag** findable: (1) add the `key: value` pair to the pinned alternation in `YAMLEmailFrontmatter.sublime-syntax`; (2) add a matching `s/^key\s*:\s*value$/name_note/;` line to `symbolIndexTransformation` in `Symbol List - Email Flags.tmPreferences`; (3) point an `open_frontmatter_symbol` entry in `francis.sublime-commands` at that token. No Python changes needed. Steps 1 and 2 must stay in step — a pair scoped but not transformed lands in the index under its raw text. **A new `class:` value needs none of this**: the syntax matches any word and the transformation captures it, so `class: X` is already indexed as `X_note`.
- Email discovery opens **no files**. Paths come from the symbol index and the displayed date/sender/subject are parsed out of the filename, whose format the Outlook macro fixes as `<prefix><yyyy-MM-dd>_<HHNN> @<sender> - <subject>.md`. Cost is therefore flat in vault size — reading frontmatter per file cost ~23ms each (cold), i.e. ~45s across 2000 emails. `read_entry_fields` is the fallback for names that don't match. The filename subject is `Left$(…, 60)` of the *sanitised* subject, so relative to the frontmatter one it is both truncated and missing any `: ? / \ " < > | [ ]`; nothing else is lost.
- `ListInputHandler.list_items()` is called once per handler activation (`setup_` in `sublime_plugin.py`), after which filtering runs natively — so typing costs nothing in Python regardless of list size. Matching is against `ListInputItem.text` only, so exactly one of sender/subject is searchable at a time — hence the `/subject` flip, which rebuilds the list with the fields swapped.
- The quick panel and input handler are one-way doors: a list goes in, an index (plus an optional `Event` of modifier keys, via `WANT_EVENT`) comes back. Neither the typed filter text nor the set of rows surviving the filter is exposed — not in `sublime.py` and not in the internal `sublime_api` either. So "act on everything currently listed" cannot be implemented, and anything needing the query text must own its own input step. `show_input_panel`'s `on_change` is the only place typed text reaches Python.
- Symbol names must be globally unique: `window.symbol_locations()` matches on name alone with no scope filter, so a bare value like `high` or `email` could collide with a symbol indexed from any other file in the project. Hence the `_note` suffix scheme. Markdown headings are indexed too, but MarkdownEditing's `symbolIndexTransformation` leaves their leading `#` intact, so they cannot collide with these.
- Keybindings use Sublime's scope-based context system — F12 dispatches to different commands based on cursor scope, and Tab opens the note picker only inside `[brackets]` in markdown files.
- **Tab is bound twice, to the same command, and both bindings are new.** `wiki_pick_link` on `meta.link.reference.description.markdown` (a `[…]`) and again on `meta.link.reference.wiki.description.markdown` (a `[[…]]`) — two bindings rather than one because scope selectors match on dot-separated prefixes and `meta.link.reference.description` is **not** a prefix of `meta.link.reference.wiki.description`. What they replaced: `mde_make_page_reference` (see the picker note above) and `mde_pick_wiki_link_page_name`, which **never existed** — no `pick_wiki` anywhere in `Installed Packages/MarkdownEditing.sublime-package`, so that binding had been dead for as long as it had been written down. MarkdownEditing binds Tab five times in markdown (`:546` `mde_complete_underlined_headings`, `:1027`/`:1039`/`:1050`/`:1060` `mde_indent_list_item`) and loads *after* this package, so it wins any overlap — but four are gated on `preceding_text` matching a bullet or a heading underline and the fifth on a **non-empty** selection, which is why `selection_empty: true` is in the context and not decoration. A todo's `[ ]` is not a hazard: `MarkdownExtended.sublime-syntax` captures the checkbox explicitly as `markup.checkbox.*.markdown-gfm`, so it never carries a link scope. `overlay_visible: false` matters because the picker re-runs the command *from* the overlay.
- **F12 in markdown is shared with MarkdownEditing, and this package cannot out-order it.** Sublime runs the *last* binding whose context matches across the merged keymap, and package order is ASCII. **The rename inverted which package that favours**: `Markdown-Note-Harness` sorts *before* `MarkdownEditing` (`-` is `0x2D`, `E` is `0x45`), so MarkdownEditing now loads later and wins every overlap — under the old name `francis_sublime_package` (`f`) it was the other way round, and the earlier version of this note said so. Nothing broke, because ordering was never what protected these bindings: ordering within `Default.sublime-keymap` only ever resolved collisions *between this package's own* bindings, and the selector was always the real tool. Where an overlap is *wanted*, see the `shift+f12` note below. MarkdownEditing binds F12 three times in markdown, all in `Default (Windows).sublime-keymap` **inside `Installed Packages/MarkdownEditing.sublime-package`** — note there is no longer a loose `Packages/MarkdownEditing/` directory at all (it once held only `plugins/wiki_page.py`), so grepping `Packages/` for these finds nothing, which is how the collision got missed once already:
  - `:1312` `mde_reference_jump` on `text.html.markdown meta.link.reference`
  - `:1323` `mde_magic_footnotes` on `text.html.markdown meta.link.reference.footnote`
  - `:1529` `mde_open_page` on `meta.link.reference.wiki.description.markdown` — **the wiki-link jump**, the one most likely to be missed, since nothing else in this package touches wiki links on F12
  Hence the `outlook_mail_action` binding's selector is `text.html.markdown - (meta.link | markup.underline.link | entity.name.attachment.yaml)`. The subtraction is MarkdownEditing's own idiom (its `:1543`) and each excluded scope is exactly the scope some other F12 binding requires. Anything new bound to F12 across the whole of `text.html.markdown` must subtract the same set. Cost of the binding: `goto_definition` in the body of a markdown file.
- **`shift+f12` is no longer untouched: it is `wiki_backlinks`, and it displaces MarkdownEditing's `mde_list_back_links` on purpose** — same question, answered by one index lookup rather than by reading every `.md` in the project. (It was never Sublime's `goto_reference` in markdown to begin with, so nothing of Sublime's own is given up.) **The selector cannot win this one and ordering now works against us**, so the handover is made deterministic by `MarkdownExtended.sublime-settings`, which sets MarkdownEditing's own `mde.keymap_disable.list_back_links` for views using this syntax. That file is a *syntax-specific* settings file, so it reaches MarkdownExtended views and nothing else, and `Packages/User/MarkdownExtended.sublime-settings` still overrides it. MarkdownEditing binds `shift+f12` three times in markdown as well (`:1317` `mde_reference_jump`, `:1328` `mde_magic_footnotes`, `:1535` `mde_list_back_links`), so the binding subtracts `meta.link` to leave the first two alone, then adds `meta.link.reference.wiki.description.markdown` back as a second alternative — MarkdownEditing excludes wiki links from back-links, so without that clause `shift+f12` would do nothing at all with the caret parked inside a link. It does **not** make the binding ask about that link: since 20260813 `wiki_backlinks` reports the note in view wherever the caret is (see the `target_name` note above). Frontmatter links need no clause: they are markdown but not `meta.link`.

## Development Notes

- No build system — this is a Sublime Text package loaded directly from the `Packages/` directory. There are three headless test suites, all run by hand and none wired to anything; nothing runs them on save or on commit.
- `tests/test_todosync.py` runs TodoSync headlessly: it stubs `sublime` / `sublime_plugin`, builds a throwaway vault in a temp directory, and drives the round trip (both completion directions, urgency both ways, deletion, the capture zone, the cold-index guard, ambiguity, CRLF preservation, idempotency). `python tests/test_todosync.py` from the package root; no Sublime needed. It has to live in `tests/` and **must never move to the package root** — it assigns a fake into `sys.modules["sublime"]` at import, so Sublime auto-loading it would break every plugin in the process.
- `tests/test_wikiresolve.py` is now a **thin plugin-layer** suite: finding the vault core, the frontmatter class gate, the `on_pre_save` buffer edit (including that it never reverts — the crash regression), and the incremental index refresh on a person-note save. It asserts BOM and CRLF survive the buffer path, because its `View` stub holds LF text with no BOM exactly as a real Sublime buffer does and translates both back on save. It skips cleanly when the vault is not present. The resolution logic is tested where it lives, with no stubbing at all: `<vault>/scripts/tests/test_wikiresolve_core.py` — discovery, the tiers, ambiguity, shapes, the meeting fold, generative-vs-reconcile, relocation and on-disk encoding. Note both files split `sublime_plugin`'s base classes in two: `TextCommand` must set `self.view`, not `self.window`, which `test_todosync.py`'s single `_Base` does not do.
- `tests/test_wikilinks.py` covers the half of `WikiLinks.py` that does not need Sublime: turning reported `(path, row)` locations into correct bytes. Specifically the measured row base (1-based, 0-based, tie, and no-fit), that **only reported rows are rewritten** so a raw `to:` line holding the same link is left alone, bracket-inclusive replacement so `[[francis]]` cannot corrupt `[[francisDennig]]`, the verify-then-skip path for a stale row, and that the BOM, CRLF, an LF-only file and a file with no trailing newline all survive byte for byte. - Four PowerShell 5.1 traps `outlook_bridge.ps1` has already been bitten by. Every one of them fails **silently** — no error, just a wrong answer — because these all sit inside `catch` blocks or count comparisons:
  - There is no try/catch **expression**. Inline `(try { $m.Subject } catch { '' })` parses as a call to a command named `try`. That is what `Read-Prop` exists for.
  - `.Count` on a bare `[pscustomobject]` is **empty**, not 1, and `return @($x)` unrolls a one-element array back to a scalar. Wrap in `@()` at every call site and before every `.Count` test.
  - A function returning an empty array yields `$null`, and **`@($null).Count` is 1** — an empty result set that reads as a unique match. Collapse with `@($x | Where-Object { $null -ne $_ })`, not `@($x)`.
  - The sender's SMTP address is `PR_SENDER_SMTP_ADDRESS` (`0x5D01001F`). `SenderEmailAddress` holds the X500 DN for Exchange senders and `PR_SMTP_ADDRESS` (`0x39FE001E`) belongs to the recipient table — both come back useless, so a sender tiebreaker built on them never fires.
